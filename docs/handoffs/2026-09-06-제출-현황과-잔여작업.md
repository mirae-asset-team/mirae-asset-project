### PR #9에서 고친 것

`GET /answer`는 주최측이 호출하는 경로인데 `verified_answer` → `agent.answer`(결정론 경로)만 불렀다. 요청 단위 렌더링·2계정 파생비율·문서형 라우팅 같은 개선분은 전부 `hcx_function_calling` 파이프라인에 있었고 그건 웹 UI 전용이라, 두 경로가 다른 답을 냈다. `main`·`agent/qa-growth-v4`·후보 `0f2fb7a` 셋 다 같은 상태였다.

**검증은 반드시 `GET /answer`로 한다.** 웹 UI(`POST /v1/hcx/function-answer`)로 보면 심사가 보지 못하는 좋은 경로를 보게 된다. 09-03 업그레이드 문서의 "외부 검증 9/9 통과"가 이 착시였고, 그래서 09-05 체크리스트가 원인을 "8000이 구 이미지"로 오진했다.

수정 후에도 provider 왕복이 깨지면(`error`·`hcx_tool_selection_failed`·`hcx_final_generation_failed`) 기존 결정론 경로로 폴백한다. `abstained`·`invalid_request`는 의도된 거절이라 그대로 반환해 투자권유·프롬프트 주입 차단을 보존한다.

## 6. 별건 — 후보 `0f2fb7a` 판정 보류

PR #8 후보의 600문항 staging 평가를 09-05 23:37~09-06 02:38에 완주했다. 결과는 pass 220 · fail 380, `hard_gate_passed=false`. 그러나 실패 380건 중 **370건이 러너 런타임 오류**(`evaluator_error` 300 · `concurrency_error` 53 · 혼합 17)이고 실제 품질 실패는 10건이다.

원인은 확인했다. 8001 컨테이너가 동시성만 20으로 올라가 있고 **분당 제한은 120 그대로**였다 — 최근 4시간 요청 5,831건 중 429/503이 1,421건(24.4%). 따라서 이 결과로 후보 품질을 판정하면 안 된다. 재실행하려면 `DISCLOSURE_PUBLIC_RATE_PER_MINUTE`를 올린 뒤 돌려야 하고 3시간과 HCX 쿼터가 든다.

주의: 후보 `0f2fb7a`에는 이번 `GET /answer` 수정이 들어 있지 않다. 재실행해서 통과하더라도 그대로 8000에 승격하면 오늘 고친 것이 되돌아간다.

또한 인수인계 러너에는 결함이 있다. `smoke_public_contracts`가 `POST /v1/answer` 응답에서 `status` 필드를 읽는데 그 엔드포인트는 `answerable`·`verified`만 반환한다 — 정상 서버에서도 **항상** 실패한다. 09-05 첫 실행은 600문항을 3시간 완주한 뒤 이 한 줄에서 예외가 나 결과 파일을 쓰기 전에 죽었다. 재실행할 때는 **산출물을 먼저 쓰고 그 다음 검증**하도록 고친 러너를 쓸 것.
